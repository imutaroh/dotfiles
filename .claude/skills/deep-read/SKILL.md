# deep-read（ディープコードリーディング）

目的は、ユーザーの頭の中に「このシステムはこう動く」という像（メンタルモデル）を作ること。読む速さではなく、分からない点を 1 つも残さないことを優先する。最初の 1 本に時間をかけるのは、そこで出来た像が、同じリポジトリの次の変更を速く読ませるから。変更を承認してよいかの判定（コードレビュー）はしない。

書籍『部下としてのAI』第 2 章で紹介されている読み方を、このスキルの手順に組み直したもの。本に書いてあることと、このスキルが足したことの区別は、末尾の「本との対応」にある。

## 守ること

- **実際のコードを読んでから話す。** 記憶や推測で説明しない。確かめていないことは「未確認」と言う
- **説明には必ずコードの場所（コードポインター）を付ける。** `path/to/file.go:42` の形で書き、ユーザーが自分の目で確かめられるようにする
- **1 メッセージで扱うのは 1 かたまりだけ。** 全部を一度に解説しない。次のかたまりへ進むのはユーザーが「次」と言ってから
- **分からない点を後回しにしない。** ユーザーが引っかかったら、先へ進まずそこを掘る。脱線ではなく本題として扱う
- **初出の用語は一言で説明する。** 仕組みの説明は「これが無いと何に困るか」から入り、身近な例は 1 つに絞る。流れは mermaid で描く
- **ライブラリや言語仕様の挙動は、公式ドキュメントか実装を確かめてから言う。** 確かめた先の URL やパスを添える
- **確認問題を出して答えを催促しない。** 理解の確認は、最後にユーザーが自分の言葉で書く説明で行う
- 読むだけ。対象のコードは書き換えない

## 進み具合のファイル

長い読解は会話の圧縮や中断で途切れる。最初に進み具合のファイルを作り、1 かたまり終えるたびに更新する。再開するときは、まずこのファイルを読む。

- 場所: 作業中のプロジェクトの `.claude/tmp/deep-read-<対象の短い名前>.md`（`.claude/tmp` が無ければ作る）
- 中身: 対象（URL やパス）／全体の地図の要約／読む順のチェックリスト（`[ ]` → `[x]`）／ユーザーが引っかかった点と、その答え／残っている疑問

同じ対象のファイルが既にあれば、新しく作らずに続きから始める。

## 手順

### 0. 対象を決める

引数で対象が決まるなら、そのまま 1 へ進む。

地図を作るには、対象のリポジトリが手元に要る。今いるフォルダが対象のリポジトリでなければ、手元の clone を探し（`gh repo view <owner>/<repo>` で名前を確かめ、ユーザーのリポジトリ置き場を見る）、見つからなければ場所を尋ねる。勝手に clone しない。以降のコマンドはそのリポジトリを指して実行する（`git -C <パス>`、`gh --repo <owner>/<repo>`）。

対象が無いときは、**そのリポジトリを最もよく知っている人の、主要なプルリクエストを 1 本だけ**選ぶ。上級者の変更には、そのリポジトリの設計の考え方が詰まっているため。候補の出し方:

```bash
# コミットの多い人を見る
git shortlog -sn --no-merges | head -10
# その人のマージ済みプルリクエストを見る
gh pr list --state merged --author <ログイン名> --limit 20
```

候補を 3 本ほど、題と変更の規模（`gh pr view <番号> --json additions,deletions,changedFiles`）を付けて見せ、ユーザーに選んでもらう。最初の 1 本は、機能の中心に触れていて、変更が大きすぎないものを勧める。

### 1. 全体の地図を作る（差分を読む前に）

いきなり差分に入らない。先にリポジトリを読んで、次を 1 画面で返す。

- **何をするシステムか**（2〜3 文）
- **ディレクトリの構成と、それぞれの役割**
- **入口（エントリーポイント）**: 処理がどこから始まるか（`main` 関数、ハンドラの登録、ジョブの定義、dbt なら対象のモデルとその上流）
- **きっかけ（トリガー）**: 何が起きたら動き出すか（HTTP リクエスト、スケジュール、メッセージの到着、手動実行）
- **入口から、今回読む場所までの流れ**（mermaid の図 1 枚）

入口ときっかけの 2 点を先に押さえるのは、あとで細かいコードを読むときに「ここは初期化」「ここはあの受け口につながる」と現在地が分かるようになるから。入口（エントリーポイント）は、HTTP の受け口を指す「エンドポイント」とは別の言葉なので、混ぜて使わない。

すべてにコードの場所を付ける。返したあと、ユーザーに像が出来たかを尋ね、ぼやけている所があればそこを掘る。像が出来てから 2 へ進む。地図の要約を進み具合のファイルに書く。

### 2. 変更の概要と、読む順を決める

プルリクエストなら `gh pr view <番号>` と `gh pr diff <番号>` を読み、次を返す。

- **この変更の目的**: 何に困っていて、どう解決したか。関連する Issue や議論があれば読む
- **変更のかたまり**: 差分を意味のまとまり（変更の種類ごと）で分ける。並べる順は、ファイル順ではなく理解しやすい順にする。土台になる型や設定 → それを使う処理 → テスト、が基本
- 各かたまりが、1 の地図のどこに当たるか

読む順をチェックリストにして進み具合のファイルに書く。プルリクエストではなくディレクトリやファイルが対象のときは、入口から呼び出しの順にかたまりを分ける。

### 3. 1 かたまりずつ読む

1 かたまりにつき、次の順で 1 メッセージにまとめる。

1. **現在地**: 地図のどこを読んでいるか（「ここは起動時の初期化」「さっきの入口から呼ばれる側」）
2. **コード**: その部分を引用して見せる（長ければ要所だけ。場所は必ず書く）
3. **何をしているか**: 処理の流れを上から順に、平易な言葉で
4. **なぜこう書いたか**: 設計の意図。ほかの書き方と比べて何が良いか。意図がコードやコミットから読み取れないときは、推測だと断って言う
5. **名前の意味**: 型・関数・変数の名前が何を表し、なぜその名前なのか。設計の型（デザインパターン）に由来する名前なら、その型を一言で説明する

最後に、引っかかった所が無いかだけを尋ねる。質問が来たら、前後のコードや呼び出し元を実際に読んで答える。質問が尽きたらチェックを付け、引っかかった点と答えを進み具合のファイルに残す。

### 4. 締め：自分の言葉で説明する

全部のかたまりを読み終えたら、ユーザーに**何も見ずに**次を書いてもらう。読んで分かった気になっている所と、説明できるまで分かっている所は、書いてみないと見分けが付かないため。

- この変更は何のためのものか
- どこから始まり、どう流れて、何が変わったか
- なぜその書き方なのか

書かれたものを実際のコードと照らし、合っている所・抜けている所・違っている所を返す。抜けと違いは、該当のかたまりへ戻って読み直す。全部が合えば完了とし、次に読むと理解が広がる対象（同じ人の別のプルリクエストなど）を 1〜2 本挙げる。

学びをノートに残すかどうかはユーザーが決める。残す先と書き方は、そのプロジェクトの決まりに従う。

## 本との対応

元にしたのは、書籍『部下としてのAI』第 2 章（ディープコードリーディング）。本に書いてあることと、このスキルが足したことを分けておく。ユーザーに「本ではどう言っているか」を聞かれたときに、スキルの決めを本の主張として答えないため。

| このスキル | 本に書いてあること（かっこ内は節の見出し） | このスキルが足したこと |
|---|---|---|
| 0. 対象を決める | 主要開発者の主な PR を 1 本だけ選ぶ（プルリクエストを100%理解する） | 候補を 3 本出して選んでもらう。手元の clone を探す |
| 1. 全体の地図 | 個別の PR を読む前に、全体の構造と動作の流れを AI に解説させ、メンタルモデルを作る。説明にはコードポインターを付けさせる。真っ先に見るのは、エントリーポイントとトリガーの 2 点（全体の構造を理解し「メンタルモデル」をつくる） | 1 画面に収める。流れを図 1 枚にする |
| 2. 変更の概要と読む順 | PR の目的と、変更の種類ごとの解説を先に出させる（プルリクエストを100%理解する） | 読む順の決め方（土台 → 処理 → テスト。ディレクトリが対象なら、入口から呼び出しの順） |
| 3. 1 かたまりずつ読む | 1 つずつ読み、引っかかったらその都度聞く（同上）。名前の理由を聞く（ネーミングにはすべて意味がある）。コードを 1 行ずつ読み、疑問をすべて潰す（たった2日で起こった大変化） | 1 メッセージで 1 かたまり。現在地 → コード → 何を → なぜ → 名前、の順 |
| 4. 締め | 学びをノートに書き残す（たった2日で起こった大変化） | 何も見ずに自分の言葉で書く。本では同じ章の会議の節（AI後の会議のテクニック）にある方法を、コードの読解に持ってきた |
| 進み具合のファイル | 計画をチェックリストのファイルにし、1 つ終えるたびに更新する。エージェントは途中で忘れるため（スラッシュコマンドテクニック） | 引っかかった点と答え、残っている疑問も書く |

本の中身を聞かれたら、スキルの文面で答えない。手元に本のテキストがあれば、該当の節を読んでから答える。無ければ「本は未確認」と言い、この表の範囲で答える。
