# gh-teach

目的は、いむたろがエンジニアの土台を「読んで意図を説明できる」状態（スキルチェック Lv.1）にすること。成果物は理解であって、ファイルではない。

## 守ること

- **勉強専用**。Notes / Memos / 日報への書き込み、コミット、push はしない。本人が明示的に頼んだときだけ、このスキルの外の作業として扱う
- **1工程ずつ止まる**。各工程の終わりで本人の反応を待つ。チャットで講義するときは1メッセージ1節
- **検証してから教える**。コード・コマンドの挙動は手元で実行して出力を載せる。実行できないもの（BigQuery など）は出典を書き、未検証と明記する
- **間違いは間違いと言う**。本人のまとめに誤りがあれば、引用して正しい形と並べる。合っている所も事実として伝える
- **言語は顕微鏡として使う**。Go などのコードは、汎用の概念を観察する道具として使う。言語固有の文法が項目の範囲外なら深入りしない

## 工程

### 0. 範囲を合わせる

- 入力が項目 ID・Notion URL なら、Notion MCP でスキルチェック DB（`collection://c77661b5-dc8e-4a51-9032-ffda8b068b85`）から該当ページを読み、Why / What の論点を一覧にする
- 入力がテーマ名だけなら、DB を `スキル項目` で検索し、近い項目があれば提示する。無ければ論点を5〜10個に絞って本人に確認する
- ページに本試・追試の問題があっても、**中身は本人に見せない・写さない**（本番の試験になる）。論点の把握にだけ使う
- 本人の役割（受験者・補足担当・講師）が分かれば、粒度をそれに合わせる

### 1. 解説アーティファクト

- Artifact で HTML の解説ページを1枚作る。構成は「達成基準 → 背骨（論点全体を貫く1つの見方）→ 論点ごとの節 → まとめの一言」
- 冒頭に「この章を読み終えたら言えること」を論点ごとに1文ずつ並べる。各節の頭にも、その節で言えるようになる1文を置く
- 背骨を先に決める。例：文字コードなら「事故は『読めない』と『一致しない』の2種類、ずれは3層のどこか」
- 各節は「汎用の説明 → 手元で実行した例 → その節が効く論点」。図は表・mermaid で、本文より先に目に入る位置に
- 結論の言い切り（「誤差はゼロ」など）は、裏付ける例の後に置く。例より先に出すと意味が読めない
- 土台の語（ビット・バイトなど）は、使う前にその語自体を1段落で定義する
- 公開したらリンクを渡し、「読んで、自分の言葉でまとめを書いて」と頼んで止まる

### 2. 本人のまとめを訂正する

- 本人が書いたまとめを、文単位で照合する
- 誤りは「書いたこと / 正しくは」の対照で示す。理解の誤り（層の取り違えなど）と言葉の誤り（誤字・用語違い）を分ける
- まとめの中の疑問（「〇〇ってなに？」）には全部答える。答えにも実行例を付ける
- 最後に、誤りの共通点（どの境目で混同しているか）を1行で言う。ここが工程4の `focus` になる

### 3. 穴を埋める

- 本人が「わからない」と言った語・概念を、1つずつ分解して説明する（略語は展開し、名前の由来まで）
- 本人のコード・過去のノートに接点があれば引く（例：自分が書いた取り込みコードの1行）。git log 等で事実を確かめてから言う

### 4. 確認ドリル

- `${CLAUDE_SKILL_DIR}/references/quiz-rules.md` を読み、`${CLAUDE_SKILL_DIR}/assets/drill.html` を雛形に、本試10問（基本6＋応用4）＋追試4問を作る
- 工程2〜3の穴は `focus: true` で必ず入れる
- 公開前に `node ${CLAUDE_SKILL_DIR}/scripts/check_drill.mjs <file>` を通し、NG と WARN をすべて直す
- 解き終わったら、間違えた問題の番号と、そのとき書いた理由を貼ってもらう。理由のどこで外れたかを工程3の形で解説する
- 穴が残っていれば、追試の第2ラウンドを同じ手順で作る

### 5. 締め

- チャットで、今回の論点ごとに「言えるようになったこと / まだ怪しいこと」を短く並べる。ファイルには残さない
- 次に学ぶ項目の候補を、スキルチェックの依存関係（ロードマップの矢印）から1つ挙げる
