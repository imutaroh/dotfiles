# technical-note

会話で身についた技術的な学びを、いむたろ様の Obsidian Vault の **tech ノート**（`type: tech`）として
「教えるのが上手い先輩エンジニア」のトーンで書き出すスキル。
コードや事実の丸写しではなく、**何か（What）→ どう使うか（How）→ つまずきどころ**の流れで、
後から読んだ本人が再現できるレベルにまとめる。「なぜ重要か」は見出しにせず What の書き出しに溶かす
（Vault 側で冒頭要約・Why 見出しは 2026-08-15 に廃止済み）。

> ⚠️ このスキルは Vault（`Notes/`）に**直接書き込む**。本来この Vault は「AI は読むだけ・
> 書き込み禁止」が原則（中核思想＝AI は自分の言葉で Vault を希釈しない）。いむたろ様が「Technical 直書き OK」と
> 明示合意した上での**異例運用**なので、後述の透明性マーカーと「自分の言葉で見直す」リマインドを必ず守る。

## 起動条件

いむたろ様が明示的に依頼したときだけ起動する（自動起動しない）。代表的なトリガー：

- 「（いまの話を）テクニカルにまとめて」「Technical ノートにして」
- 「Obsidian のテクニカルに保存して」「この概念をテクニカルノート化して」
- 「○○を Technical に」

## ネタ元（インプット）の制約

**次の2つだけをネタ元にする。これ以外から内容を足さない。**

1. **直近の会話履歴** — いまのセッションで Claude が説明した／話題に出た技術概念
2. **明示的に渡されたコード/ファイル** — パスやコードスニペットを渡されたら、それを読んで解説する

やらないこと：

- 勝手な Web 調査・外部リサーチ（必要だと思っても、足りない箇所は本文に「未確認」と書いて止める）
- `Notes/` の既存ノートの**書き換え**（このスキルが触るのは新規 or 明示指定の Technical ノートだけ）
- ネタ元が曖昧なときの推測。何をまとめるのか1問だけ確認してから書く

## 出力仕様

> [!warning] 書式の正本は Vault 側にある
> ファイル名・frontmatter・見出し規約の**正本は `Notes/CLAUDE.md`**（Vault のゾーン規約）。
> 書き始める前に必ずそのファイルを読み、**そこに書いてある規約を優先する**。
> このスキルに書式を書き写すと必ず陳腐化する（実際 2026-08-16 に、スキル側が旧規約のまま
> 3箇所ずれているのが見つかった）。以下は「読むまでもない要点」の控えであり、
> `Notes/CLAUDE.md` と食い違ったら**向こうが正しい**。

### 置き場所（固定）

```
/Users/imutaakihiro/repos/imutaakihiro/ObsidianImus/Notes/{自然なタイトル}.md
```

> このパスはハードコード。別マシン／パス変更で壊れる前提（パーソナル運用なので許容）。

### ファイル名（要点の控え）

- **ファイル名＝公開ページのタイトル＝URL**。判定基準は「文中にリンクとして置いたとき、読者がクリック前に中身を予想できるか」
- **自然なタイトルにする。ツール・技術名をどこかに含める**（検索で拾うため。先頭でなくてよい）
  例：`BigQueryのウィンドウ関数`、`herdrにClaude Codeのセッション名を出す`
- 旧 `{対象} - {トピック}` 形式は 2026-08-12 に格下げ済み。**新規では使わない**
- 禁止：「〜について」「〜まとめ」「〜メモ」等の中身が予想できない語尾／日付・実名／記号・絵文字。目安30字以内
- 書く前に `Notes/` の既存ファイル一覧を確認する。**同名衝突に注意**（フラット構造）
- **同名ファイルがあったら上書きしない。**「追記するか・別名にするか」を1問確認する

### frontmatter（要点の控え）

```yaml
---
type: tech
tags:                   # 統制語彙10個からのみ選ぶ（ai / dev / data / marketing /
  - dev                 # growth-hack / self-management / health / mindset / people / goals）
                        # 該当が無ければ tags: [] のまま。type の言い換えは入れない
created: {YYYY-MM-DD}   # date コマンドで取得した当日（推測で書かない）
source: claude-draft    # AI が会話から下書きした透明性マーカー（自分の言葉で見直したら外してよい）
permalink: {kebab-case} # 必須。英小文字ケバブケースで意味を英訳する
---
```

### 本文の型（What / How）

- **本文にタイトル見出しを書かない**（Publish がファイル名をページタイトルとして表示するため二重になる）
- **冒頭要約・summary callout は置かない**（2026-08-15 に全廃）。frontmatter の直後は最初の見出しから始める
- **見出しは `##` から**。`#` と `###` 始まりは使わない
- 軸は `## What`（概念・仕組み）→ `## How`（使い方・実例）。内容に応じて見出しを足してよい
  （例：`## 落とし穴`）。見出しに内容を持たせる（`## What — 2行目はモデル名ではない` のように後置きで補ってよい）
- **末尾は `## 関連`**：トピックページ1本以上＋既存ノートへの横リンク1本以上
- 目標長 400〜1200字。1500字を超えるなら分割する

### トーン・作法（Notes/ の原則を厳守）

- **自分の言葉で**。会話やコードの丸写しをしない。要点を噛み砕いて書く
- **リンクで繋ぐ**：関連する既存ノートがあれば `[[xxx|表示テキスト]]` の名前リンクで繋ぐ。
  実在を確認できたノートだけリンクする（存在しないノートへ無闇にリンクしない）
- 簡潔に。冗長な前置きや一般論で埋めない（既存 Technical ノートは短くて濃い）
- Callout を使うなら `[!info]` `[!warning]` `[!success]` の3種のみ

## 手順

1. **ネタ元を確定**：会話履歴か、渡されたコード/ファイルか。曖昧なら「何を Technical にまとめますか？」と1問だけ聞く
2. **書式の正本を読む**：`ObsidianImus/Notes/CLAUDE.md` を Read する（**必須・スキップ不可**）。
   Vault の外（`~/dotfiles` など）で作業していると自動読み込みされないので、自分で読みに行く。
   このスキルの記述と食い違ったら Vault 側に従い、**食い違いを完了報告で1行伝える**（スキル側を直す起点にする）
3. **当日の日付を取得**：`date +%Y-%m-%d`
4. **既存一覧を確認**：`Notes/` を `ls`/Glob で見て、命名の流儀と重複をチェック
5. **同名があれば確認**：追記 or 別名をいむたろ様に確認
6. **既存ノートを実物で確認**：直近に書かれた同種の tech ノートを1本 Read し、書式の実例を掴む
   （規約文よりも実物のほうが速い）。同時に、リンクできる関連ノートを Grep/Glob で探す
7. **本文を組み立て**：`## What` / `## How` / `## 関連`。frontmatter を付ける（`permalink` の埋め忘れに注意）
8. **直接 Write**：上記パスに書き出し、**該当トピックページ（例: [[開発環境]]・[[GitHub]]、無ければ [[Tech]]）にリンクを1行追記する**（幽霊ノート予防。Notes/CLAUDE.md の常設許可範囲）
   - 長くなる場合は骨子を `Write` → 各節を `Edit` で継ぎ足す（一発 Write でツール呼び出しが壊れるのを防ぐ）
9. **完了報告**：書き出したパス・見出し構成・貼った関連リンクを伝える。
   最後に必ず一言：「**自分の言葉で一度見直すと第二の脳に定着します**（`source: claude-draft` は見直したら外してOK）」

## 完了報告のフォーマット例

```
✅ tech ノートを作成しました
- パス: Notes/○○.md
- 構成: ## What / ## How / ## 関連
- 結線: トピックページ [[...]] に1行追記 ／ 横リンク [[...]]（n本）

自分の言葉で一度見直すと第二の脳に定着します。
（AI 下書きマーカー source: claude-draft は、見直したら外してOK）
```
