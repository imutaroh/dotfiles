# /close — セッション振り返りレビュー

## このスキルの目的

**いむたろ様が Claude Code をよりうまく使えるようになること。** 成果物の品質評価ではない。

見るのは「Claude が何を計画し、何を実装し、結果どうなったか」の記録だが、
そこから引き出すのは **指示の出し方・前提の与え方・介入のタイミング** の改善点である。

## やらないこと（責務の固定）

- コードの品質レビュー（`/code-review` の担当）
- コミット・push・PR 操作（`/close` という名前に釣られて片付けを始めない）
- 成果物の作り直し
- **会話コンテキストの記憶に頼った振り返り（禁止）**。証拠は生のセッションログのみ

---

## 手順

### Step 1. セッションログを読める形に変換する

メインセッションが同梱スクリプトを実行する。**出力した生ログをメインは読まない**
（レビューはサブエージェントの仕事であり、メインが読むとコンテキストを二重に消費するため）。
メインが読んでよいのは Step 5 で、検証を通ったレビュー結果のファイルだけ。

**引数なしで呼んではいけない**（`ls -t` で最新更新の jsonl を掴むため、並行セッションがあると別セッションをレビューする。2026-08-12 に実際に発生し、opus のレビュー1本＋検証1本が丸ごと無駄打ちになった）。

**自セッションの `session_id` を明示して呼ぶ。** ID はシステムプロンプトの scratchpad パス
（`/private/tmp/claude-*/<プロジェクト>/<session_id>/scratchpad`）に入っているので、そこから取る。

```bash
~/.claude/skills/close/extract-session.sh \
  .claude/tmp/close/session-<session_id先頭8桁>.md \
  ~/.claude/projects/<プロジェクトのスラッグ>/<session_id>.jsonl
```

出力パスとバイト数が返る。**続けて、抽出したログが自分のセッションかを1行で照合する**（例: `grep -c "<今回だけ出た固有語>" <出力パス>` か、`head` で冒頭のユーザー発言が自分への最初の依頼と一致するか）。
照合せずに Step 3 へ進むと、別セッションのレビューを作ってから気づくことになる。

**ctx（`ctx search` / `ctx show session`）を使ってはいけない。**
一見この用途に合っているが、実測で以下が判明している：

- ctx の自動インデックスは進行中セッションを含まない（実測で7時間以上の遅れ）
- 手動 `ctx import` で取り込んでも、**62イベント中58件が `content_retention: metadata_only`** になる
- 消えるのは tool_call の入力・tool_output の中身・**AskUserQuestion の回答**
- これは設定ミスではなく ctx の設計方針（`ctx docs show provider-import-policy` の
  "Native imports should not store or index by default" を参照）。設定で戻せない

つまり ctx 経由だと「いむたろ様が何を選んだか」が丸ごと消え、
このスキルが最も見たい部分が欠落する。生ログを直接読むこと。

スクリプトが失敗した場合は、**振り返りを捏造せずここで止めて報告する。**
記憶で代用してはいけない。

### Step 2. サイズを測ってモデルを決める

Step 1 が返したバイト数で分岐する。サブエージェントのモデルは**必ず明示指定**する。

| 出力サイズ | モデル | 読み方 |
|---|---|---|
| 80 KB 未満 | `sonnet` | 全文を読む |
| 80 KB 以上 200 KB 以下 | `opus` | 全文を読む |
| 200 KB 超 | `opus` | 先頭200行（＝最初の指示＝本来の意図）＋末尾を読む。**削った事実を出力に明記させる** |

長いセッションほど「いつのまにか本来の目的からズレていた」が起きやすく、
その切り分けは微妙な判断になるため上位モデルを割り当てる。

Step 4 の検証エージェントは**サイズによらず `sonnet` 固定**。
やるのは引用の文字列突合と前後文脈の確認であり、判断の余地が小さいため。

### Step 3. レビューサブエージェントを起動する

`Agent` ツール（`subagent_type: "general-purpose"`、`model` は Step 2 で決めた値）に、以下をそのまま渡す。
**ログの中身をメインが要約して渡してはいけない。パスだけ渡す。**
要約して渡した時点で「メインの自己弁護をロンダリングしただけ」になり、第三者性が消える。

レビュー結果は**ファイルに書かせ、返り値はパスだけにする**。
メインが本文を受け取ると、まだ検証を通っていない指摘がメインのコンテキストに居座り、
Step 4 で落としたはずの引用が Step 5 で復活する。

````
あなたはセッションレビュー担当です。ユーザー（いむたろ様）が Claude Code をより
うまく使えるようになることだけが目的です。成果物の品質評価はしません。

## 材料
- 生ログ: {Step 1 の出力パス}
- 過去の指摘台帳: ~/.claude/skills/close/ledger.md
- 出力先: {生ログと同じディレクトリ}/review-{session_id}.md

これは Claude Code のセッションの生ログを読める形に変換したものです。
`## user` / `## assistant` が発言、`### TOOL:` が Claude のツール実行、
`### RESULT` がその結果です。AskUserQuestion の回答は `### RESULT` の中に
「The user answered: ...」の形で入っています。

まず `wc -c` でサイズを測り、{Step 2 の読み方} に従って読んでください。
一部しか読めなかった場合は、その事実を出力の冒頭に必ず書いてください。

このファイルが唯一の証拠です。ここに書かれていないことは推測しないでください。
なお TOOL の入力と RESULT は先頭 800 文字で打ち切られています。
「証拠が見つからなかった」ことを「問題がなかった」と読み替えないでください。

## 台帳の使い方（先に読む）

`ledger.md` は過去の `/close` で出た指摘の一覧です。**改善ラダーの1段/2段の判定にだけ使います。**
同じ趣旨の指摘が過去にもあるなら、それは「今回限り」ではなく「また起きている」ので2段以上に上げる。
何回目かを出力に書いてください（例:「台帳に同趣旨が2件。今回で3回目」）。

**台帳を証拠に使ってはいけません。** 今回の生ログから引用が取れない指摘は、
台帳に何が書かれていても出さないでください。台帳を埋めるために指摘を作るのも禁止です。

## 分岐点の探し方

主観で「重要そうな瞬間」を探さないでください。まず以下をログから機械的に拾い、
その周辺だけを分岐点の候補として精査します。

- いむたろ様の**訂正・否定・軌道修正**の発言（「違う」「そうじゃない」「戻して」「やめて」「そうではなく」）
- **手戻り**（一度書いたものを取り消す、実装後に方針が変わる、同じファイルを何度も直す）
- **同一ツールの反復失敗**（同じコマンドが3回以上エラーになっている）
- **拒否されたツール呼び出し**、および確認を挟まずに外部へ書き込んだ箇所
- いむたろ様の**長い自由記述**（選択式の回答ではなく、まとまった文章で指示している箇所）

これらは候補を見つける入口であって、**それ自体を指摘として出力しないでください。**
このレビューの重心は「いむたろ様の指示の出し方」のままです。
Claude 側の逸脱を網羅的に洗い出す作業に広げてはいけません。

## 鉄則
1. **引用できない指摘は出さない。** すべての指摘に、ログからの実際の発言引用
   （20〜80字程度）を添えること。引用が作れない指摘は、その時点で捨てる。
2. **抽象的な助言を禁止する。** 「指示を具体的に」「前提を先に伝える」のような、
   どのセッションにも当てはまる文言は価値がゼロなので書かない。
   このセッションで実際に起きたことにしか言及しない。
3. **責任を切り分ける。** 各指摘について「指示側の問題」「Claude 側の問題」
   「どちらでもない（情報不足・環境要因）」のどれかを明示する。
   Claude 側の問題を指示側のせいにしない。逆もしない。
4. **お世辞を書かない。** 良かった点は1つだけ挙げてよいが、
   「なぜうまくいったか」の再現条件まで書けないなら書かない。
5. ログの生データ・秘密情報・長いパスをそのまま貼らない。

## 出力形式（この順で、日本語）

### 1行要約
このセッションで何が起きたか。1文。

### 分岐点 Top3
セッションの結果を最も左右した瞬間を3つまで。少なければ少なくてよい。各項目：
- **引用**: 実際の発言（誰の発言かを明記）
- **何が起きたか**: その後どうなったか
- **責任の所在**: 指示側 / Claude 側 / どちらでもない
- **代わりにどうすればよかったか**: 具体的な行動

### 次回そのまま使えるプロンプト書き換え案
1〜2個。「こう言えばよかった」を、コピペで使える日本語のプロンプト文として書く。
感想ではなく、再利用できる資産として書くこと。
無理に作らない。材料が無ければ「該当なし」と書く。

### 改善ラダーの提案
気づきの寿命に応じて、着地先を提案する。該当なしなら「1段のみ」と書く。
各項目に**台帳での再発回数**を添える（初出なら「初出」と書く）。
- 1段: 今回限り → 会話で読んで終わり
- 2段: また起きそう → CLAUDE.md か memory へのルール追加（**追加する文面を実際に書く**）
- 3段: 手順が固まった → Skill 化（スキル名と責務を1行で）
- 4段: 人間が忘れる／自動化したい → hooks / settings.json（**どのフックイベントで何をするかまで書く**）

## 出力方法

上記の内容を **出力先のパスに Write してください**。
あなたが最後に返すのは **そのファイルパス1行だけ** です。本文を返り値に含めないでください。
````

### Step 4. 引用を検証する

レビューを書いた本人に自己採点させても意味がないため、**別のサブエージェントに突合させる**。
`Agent` ツール（`subagent_type: "general-purpose"`、`model: "sonnet"`）に以下を渡す。

````
あなたは引用の検証担当です。レビューの中身の良し悪しは判断しません。
**引用がログに実在するか**と、**引用の解釈がログと矛盾していないか**だけを見ます。

## 材料
- 検証対象のレビュー: {Step 3 が返したパス}
- 元の生ログ: {Step 1 の出力パス}

## 手順
1. レビューに含まれるすべての引用を列挙する。
2. 各引用について、`grep -F` で生ログに実在するか確認する
   （表記ゆれで空振りすることがあるので、落ちたものは特徴的な部分文字列で再検索する）。
3. 実在した引用は、生ログでのその**前後を読む**。
   引用の切り取り方によって、発言の意図が反対の意味に変わっていないか確認する。
   例: 撤回された案を、採用された案であるかのように引用していないか。
4. レビューが「誰の発言か」を取り違えていないか確認する（user と assistant の入れ替わり）。

## 判定と処置
- **引用がログに実在しない指摘** → その指摘をレビューから削除する。
- **引用は実在するが、前後を読むと意味が反転している指摘** → 削除する。
- **話者を取り違えている指摘** → 責任の所在が逆になるので削除する。
- 疑わしいが判断がつかないものは削除せず、指摘の末尾に `（検証: 判断保留）` と付ける。

レビューのファイルを上書きし、冒頭に検証結果を1行で書き足すこと:
`> 検証: 引用N件を突合し、M件の指摘を削除（理由）`

## 返り値
**検証件数・削除件数・削除理由だけ**を数行で返す。レビュー本文は返さない。
````

削除が多すぎる（例: 指摘の半分以上が落ちた）場合は、レビュー側の問題なので
**Step 5 でその事実をいむたろ様に必ず伝える**。黙って残りだけ提示しない。

### Step 5. 結果をメインが要約して提示する

サブエージェントの出力はいむたろ様には折りたたまれて見えないため、
メインが Step 3 の出力ファイル（Step 4 で検証済み）を読み、**自分の言葉で日本語にして提示する**。
完了報告だけで済ませない。

**引用はファイルにある文字列を一字一句そのまま貼る。** 縮めない、言い換えない、要約しない。
引用が消えたり変形したりすると、鉄則1と Step 4 の検証がまとめて無意味になる。
冒頭に対象の `session_id` と Step 4 の検証結果（1行）を必ず表示し、
別セッションを掴んでいないか・指摘がどれだけ落ちたかに気づける状態にする。

### Step 6. 昇格の判定と反映

- **1段のみ**なら、反映は無し。ただし **Step 7 の台帳追記は行う**（省略不可）。
  `.claude/tmp/` のファイルは消さずそのままでよい（gitignore 済み）。
- **2段以上が出たら、必ずいむたろ様の承認を取ってから反映する。** 勝手に CLAUDE.md を書き換えない。
  - CLAUDE.md / memory への追記 → 承認後に反映
  - Skill 化 / hooks → 別セッションの作業として提案するに留める（`/close` の中で実装まで進めない）
- **昇格が発生した回だけ**、Obsidian 日報（`Private/Journals/YYYY-MM-DD.md`）に追記する。
  日付は `date` コマンドで取得する。セクション見出しは `## セッション振り返り`。
  昇格がなかった回は日報に書かない（ノイズで日報が埋まるのを防ぐ）。

### Step 7. 台帳に追記する（毎回・省略不可）

`~/.claude/skills/close/ledger.md` の表に **1回1行**追記する。
**昇格が無かった回も「該当なし」で必ず1行足す。** ここを省くと台帳が昇格した指摘だけの
偏った記録になり、「また起きそう」の判定が使い物にならなくなる。

| 列 | 入れるもの |
|---|---|
| 日付 | `date` コマンドで取得した YYYY-MM-DD |
| session_id | Step 1 が返した id の先頭8桁 |
| 指摘の1行要約 | 具体的に。「指示が曖昧だった」のような汎用文は書かない |
| 判定 | `2段` / `3段` / `4段` / `却下` / `該当なし` |
| 着地先 | 反映先のファイル名、または却下理由 |

台帳は dotfiles 管理下（`~/.claude/skills` は dotfiles へのシンボリックリンク）なので、
書き込むとリポジトリの差分になる。**コミットはしない。** いむたろ様が判断する。

### Step 7.5. プロンプト書き換え案を prompts.md に追記する（出た回のみ）

レビューの「次回そのまま使えるプロンプト書き換え案」が該当なし以外だった回は、
`~/.claude/skills/close/prompts.md` にも追記する（貯める場所＝まとまった場所。後でまとめる工程を作らない）。

- 1案 = 1エントリ。見出しに「いつ使うか」の状況、本文にレビューのプロンプト文をそのまま貼る
- 日付・session_id を添える（台帳と突合できるように）
- 該当なしの回は何もしない。**プロンプト集を埋めるために案をひねり出さない**（レビューの「無理に作らない」と同じ鉄則）
- 読み返し・選別はいむたろ様が月次振り返りのタイミングで行う。自動化しない。コミットもしない

## この設計が壊れる条件

- **~~`ls -t` で現セッションを特定している。~~** → 2026-08-12 に実際に別セッション（並行して走っていた Zenn 作業）を掴んだため、Step 1 を **session_id 明示必須＋抽出後の照合** に変更した。スクリプト自体は引数なしでも動くので、**呼び方を間違えれば再発する**。Step 5 で `session_id` を必ず表示するのはこのため。
- **thinking ブロックは暗号化されており本文が存在しない。** Claude が「なぜそう判断したか」の
  内心は証拠として取れない。取れるのは発言と行動だけ。内心を推測させない。
- **TOOL 入力と RESULT は 800 文字で打ち切っている。** 長い出力の後半で起きた失敗は見えない。
  必要なら `TOOL_RESULT_MAX=3000 ~/.claude/skills/close/extract-session.sh` で伸ばせるが、
  その分サブエージェントのコンテキストを食う。
- **セッションの途中で `/close` を呼ぶと、作業未完了の状態をレビューすることになる。**
  「記録が Write 直後で切れている」ようなレビュー結果が出たら、それは作業が終わっていない証拠。
  区切りがついてから呼ぶこと。
- **台帳はレビュアーに予断を与える。** 「前にも同じ指摘があった」を先に読むと、
  今回のログに根拠が無くても再発認定を始める。Step 3 のプロンプトで
  「台帳を証拠に使うな」と縛っているが、これが破られたら鉄則1は骨抜きになる。
  レビュー出力に「台帳では3回目」とあるのに今回の引用が添えられていなかったら、その指摘は捨てる。
- **Step 4 の検証は引用の実在と前後関係しか見ない。** 引用が本物で解釈も歪んでいなくても、
  そこから導いた「代わりにどうすればよかったか」が的外れである可能性は残る。
  検証を通ったことは「証拠が本物」の保証であって、「提言が正しい」の保証ではない。
- **台帳が増えると Step 3 のコンテキストを食う。** 数十行なら問題ないが、
  百行を超えたら古い「該当なし」行を畳む（件数だけ残す）必要が出る。まだその時期ではない。

## 「該当なし」は正常な出力である（鉄則を緩めないこと）

このスキルの重心は「いむたろ様の使い方の改善」なので、材料はいむたろ様の**自由記述**しかない。
AskUserQuestion の選択式回答が中心の回（設計の壁打ちなど）では、批評する対象がそもそも
存在しないため、「プロンプト書き換え案：該当なし」「改善ラダー：1段のみ」が正常な結果になる。

実測でも、このスキルを作ったセッション自身を2回レビューして2回とも書き換え案は該当なしだった。

**「該当なしが続くから」という理由で、以下を緩めてはいけない。**

- 鉄則1（引用できない指摘は出さない）
- 鉄則2（抽象的な助言の禁止）
- レビューの重心を「Claude 側の逸脱検出」に広げること

緩めた瞬間、「指示を具体的に」級の無内容な提言が毎回出るようになり、読まれなくなって
スキルごと死ぬ。空振りは正直な結果として受け入れる、というのがいむたろ様の判断である
（2026-08-10 決定）。`/close` が効くのは、長い自由記述で指示して実装させた回。
