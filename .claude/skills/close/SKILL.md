# /close — セッション振り返りレビュー

## このスキルの目的

**いむたろ様が Claude Code をよりうまく使えるようになること。** 成果物の品質評価ではない。

見るのは「Claude が何を計画し、何を実装し、結果どうなったか」の記録だが、
そこから引き出すのは **指示の出し方・前提の与え方・介入のタイミング** の改善点である。

## やらないこと（責務の固定）

- コードの品質レビュー（`/code-review` の担当）
- コミット・push・PR 操作（`/close` という名前に釣られて片付けを始めない）
- 成果物の作り直し
- **会話コンテキストの記憶に頼った振り返り（禁止）**。証拠は生のセッションログのみ

---

## 手順

### Step 1. セッションログを読める形に変換する

メインセッションが同梱スクリプトを実行する。**出力したファイルをメインは読まない**
（レビューはサブエージェントの仕事であり、メインが読むとコンテキストを二重に消費するため）。

```bash
~/.claude/skills/close/extract-session.sh
```

出力パス（`.claude/tmp/close/session-<id>.md`）とバイト数が返る。
引数で対象を明示することもできる: `extract-session.sh <出力先> <対象jsonl>`

**ctx（`ctx search` / `ctx show session`）を使ってはいけない。**
一見この用途に合っているが、実測で以下が判明している：

- ctx の自動インデックスは進行中セッションを含まない（実測で7時間以上の遅れ）
- 手動 `ctx import` で取り込んでも、**62イベント中58件が `content_retention: metadata_only`** になる
- 消えるのは tool_call の入力・tool_output の中身・**AskUserQuestion の回答**
- これは設定ミスではなく ctx の設計方針（`ctx docs show provider-import-policy` の
  "Native imports should not store or index by default" を参照）。設定で戻せない

つまり ctx 経由だと「いむたろ様が何を選んだか」が丸ごと消え、
このスキルが最も見たい部分が欠落する。生ログを直接読むこと。

スクリプトが失敗した場合は、**振り返りを捏造せずここで止めて報告する。**
記憶で代用してはいけない。

### Step 2. サイズを測ってモデルを決める

Step 1 が返したバイト数で分岐する。サブエージェントのモデルは**必ず明示指定**する。

| 出力サイズ | モデル | 読み方 |
|---|---|---|
| 80 KB 未満 | `sonnet` | 全文を読む |
| 80 KB 以上 200 KB 以下 | `opus` | 全文を読む |
| 200 KB 超 | `opus` | 先頭200行（＝最初の指示＝本来の意図）＋末尾を読む。**削った事実を出力に明記させる** |

長いセッションほど「いつのまにか本来の目的からズレていた」が起きやすく、
その切り分けは微妙な判断になるため上位モデルを割り当てる。

### Step 3. レビューサブエージェントを起動する

`Agent` ツール（`subagent_type: "general-purpose"`、`model` は Step 2 で決めた値）に、以下をそのまま渡す。
**ログの中身をメインが要約して渡してはいけない。パスだけ渡す。**
要約して渡した時点で「メインの自己弁護をロンダリングしただけ」になり、第三者性が消える。

````
あなたはセッションレビュー担当です。ユーザー（いむたろ様）が Claude Code をより
うまく使えるようになることだけが目的です。成果物の品質評価はしません。

## 材料
{Step 1 の出力パス}

これは Claude Code のセッションの生ログを読める形に変換したものです。
`## user` / `## assistant` が発言、`### TOOL:` が Claude のツール実行、
`### RESULT` がその結果です。AskUserQuestion の回答は `### RESULT` の中に
「The user answered: ...」の形で入っています。

まず `wc -c` でサイズを測り、{Step 2 の読み方} に従って読んでください。
一部しか読めなかった場合は、その事実を出力の冒頭に必ず書いてください。

このファイルが唯一の証拠です。ここに書かれていないことは推測しないでください。
なお TOOL の入力と RESULT は先頭 800 文字で打ち切られています。
「証拠が見つからなかった」ことを「問題がなかった」と読み替えないでください。

## 鉄則
1. **引用できない指摘は出さない。** すべての指摘に、ログからの実際の発言引用
   （20〜80字程度）を添えること。引用が作れない指摘は、その時点で捨てる。
2. **抽象的な助言を禁止する。** 「指示を具体的に」「前提を先に伝える」のような、
   どのセッションにも当てはまる文言は価値がゼロなので書かない。
   このセッションで実際に起きたことにしか言及しない。
3. **責任を切り分ける。** 各指摘について「指示側の問題」「Claude 側の問題」
   「どちらでもない（情報不足・環境要因）」のどれかを明示する。
   Claude 側の問題を指示側のせいにしない。逆もしない。
4. **お世辞を書かない。** 良かった点は1つだけ挙げてよいが、
   「なぜうまくいったか」の再現条件まで書けないなら書かない。
5. ログの生データ・秘密情報・長いパスをそのまま貼らない。

## 出力形式（この順で、日本語）

### 1行要約
このセッションで何が起きたか。1文。

### 分岐点 Top3
セッションの結果を最も左右した瞬間を3つまで。少なければ少なくてよい。各項目：
- **引用**: 実際の発言（誰の発言かを明記）
- **何が起きたか**: その後どうなったか
- **責任の所在**: 指示側 / Claude 側 / どちらでもない
- **代わりにどうすればよかったか**: 具体的な行動

### 次回そのまま使えるプロンプト書き換え案
1〜2個。「こう言えばよかった」を、コピペで使える日本語のプロンプト文として書く。
感想ではなく、再利用できる資産として書くこと。
無理に作らない。材料が無ければ「該当なし」と書く。

### 改善ラダーの提案
気づきの寿命に応じて、着地先を提案する。該当なしなら「1段のみ」と書く。
- 1段: 今回限り → 会話で読んで終わり
- 2段: また起きそう → CLAUDE.md か memory へのルール追加（**追加する文面を実際に書く**）
- 3段: 手順が固まった → Skill 化（スキル名と責務を1行で）
- 4段: 人間が忘れる／自動化したい → hooks / settings.json（**どのフックイベントで何をするかまで書く**）
````

### Step 4. 結果をメインが要約して提示する

サブエージェントの出力はいむたろ様には折りたたまれて見えないため、
**メインが自分の言葉で日本語にして提示する**。完了報告だけで済ませない。

引用は落とさずに残すこと。引用が消えると、鉄則1が意味を失う。
冒頭に対象の `session_id` を必ず表示し、別セッションを掴んでいないか気づける状態にする。

### Step 5. 昇格の判定と反映

- **1段のみ**なら、ここで終了。ファイルもそのまま（`.claude/tmp/` は gitignore 済み）。
- **2段以上が出たら、必ずいむたろ様の承認を取ってから反映する。** 勝手に CLAUDE.md を書き換えない。
  - CLAUDE.md / memory への追記 → 承認後に反映
  - Skill 化 / hooks → 別セッションの作業として提案するに留める（`/close` の中で実装まで進めない）
- **昇格が発生した回だけ**、Obsidian 日報（`Vault/03_Journals/YYYY-MM-DD.md`）に追記する。
  日付は `date` コマンドで取得する。セクション見出しは `## セッション振り返り`。
  昇格がなかった回は日報に書かない（ノイズで日報が埋まるのを防ぐ）。

## この設計が壊れる条件

- **`ls -t` で現セッションを特定している。** 同じプロジェクトで別の Claude Code セッションが
  並行して動いていると、そちらを掴む可能性がある。Step 4 で `session_id` を必ず表示する理由。
- **thinking ブロックは暗号化されており本文が存在しない。** Claude が「なぜそう判断したか」の
  内心は証拠として取れない。取れるのは発言と行動だけ。内心を推測させない。
- **TOOL 入力と RESULT は 800 文字で打ち切っている。** 長い出力の後半で起きた失敗は見えない。
  必要なら `TOOL_RESULT_MAX=3000 ~/.claude/skills/close/extract-session.sh` で伸ばせるが、
  その分サブエージェントのコンテキストを食う。
- **セッションの途中で `/close` を呼ぶと、作業未完了の状態をレビューすることになる。**
  「記録が Write 直後で切れている」ようなレビュー結果が出たら、それは作業が終わっていない証拠。
  区切りがついてから呼ぶこと。

## 「該当なし」は正常な出力である（鉄則を緩めないこと）

このスキルの重心は「いむたろ様の使い方の改善」なので、材料はいむたろ様の**自由記述**しかない。
AskUserQuestion の選択式回答が中心の回（設計の壁打ちなど）では、批評する対象がそもそも
存在しないため、「プロンプト書き換え案：該当なし」「改善ラダー：1段のみ」が正常な結果になる。

実測でも、このスキルを作ったセッション自身を2回レビューして2回とも書き換え案は該当なしだった。

**「該当なしが続くから」という理由で、以下を緩めてはいけない。**

- 鉄則1（引用できない指摘は出さない）
- 鉄則2（抽象的な助言の禁止）
- レビューの重心を「Claude 側の逸脱検出」に広げること

緩めた瞬間、「指示を具体的に」級の無内容な提言が毎回出るようになり、読まれなくなって
スキルごと死ぬ。空振りは正直な結果として受け入れる、というのがいむたろ様の判断である
（2026-08-10 決定）。`/close` が効くのは、長い自由記述で指示して実装させた回。
