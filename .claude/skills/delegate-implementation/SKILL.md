# Delegate Implementation

実装をサブエージェント（`subagent_type: "general-purpose"`）に切り出して実行し、メインセッションは設計・監査・レビューに専念する。目的はコンテキスト温存とモデル単価の適材適所。

`$ARGUMENTS` があればそれを対象タスクとし、なければ進行中のタスクに適用する。

## 役割分担

| 担当 | 仕事 |
|------|------|
| メイン | 要件整理・設計・タスク分解・委譲プロンプト作成・成果物の監査/レビュー・統合判断・最難関部分の実装 |
| サブエージェント | 設計に沿った実装・テスト作成・機械的な修正・定型作業 |

## モデル選定（2026-07時点、四半期ごとに見直す）

Agent ツールの `model` パラメータで指定する。

- **sonnet（既定）**: 既存パターンの踏襲、定型実装、テスト追加、ドキュメント更新、単一〜少数ファイルの修正。Sonnet 5 は知識ワーク・定型実装で旧世代 Opus 同等の実力かつ低単価
- **opus（例外）**: 軽い設計判断を含む実装・複数ファイル横断のリファクタで、sonnet では品質が足りないと確認できたときだけ
- **fable は委譲先にしない**: 高単価かつ文章・ドキュメント品質が弱い実測あり。fork も同モデル・同履歴で節約にならない
- **effort は指定しない**（デフォルト high）。失敗時はまず委譲プロンプトの情報不足を疑い、それでも浅い場合のみ上げる
- **メインが直接実装**するのは: 誤実装のリカバリコストが高い微妙な処理／会話文脈と実装が不可分／サブエージェントが2回失敗、のいずれかだけ
- 詳細は Vault の `Technical - Claude - モデル使い分けとeffort運用` を参照

## ワークフロー

1. **設計**: 実装前に設計案を提示（複数案 → メリット/デメリット → 1案選定 → 破綻条件の明示。グローバル指示の設計フェーズに従う）
2. **分解**: 独立して実装できる単位に分割し依存関係を明確化。独立タスクは1メッセージ内で複数 Agent を並列起動する
3. **委譲**: サブエージェントは会話コンテキストを共有しない。プロンプトに必ず含める: 対象ファイルの絶対パス／期待成果物と完了条件／従うべき規約／スコープ外／検証方法（テスト・ビルドを通すまでが仕事）。並列で同一リポを書き換える場合は `isolation: "worktree"`
4. **監査**: 成果物はエージェントの自己申告ではなく `git diff` を読んでレビューし、テスト・ビルドを実行して確認。NG なら新規 spawn せず SendMessage で同じエージェントに修正指示（2回失敗したらメインが引き取る）
5. **報告**: サブエージェントの出力はユーザーに折りたたまれて見えない。何をどう実装しどう検証したかを自分の言葉で要約する

## 委譲しない判断（節約の罠）

委譲はコンテキスト再送を伴うため、小さいタスクではかえってトークンが増える。

- 数行の修正・単発の小さい編集 → メインが直接やる
- 設計と実装が不可分な探索的タスク → 分業しない
- 委譲プロンプトが実装と同等以上の分量になりそう → メインが直接やる

## 原則

- サブエージェントに git 操作（add / commit / push / branch）と仕様外のファイル変更をさせない
- イシュー・ブランチ運用など CLAUDE.md の Git 開発フローは通常どおり従う
- レビューは省略しない。委譲した実装の品質責任はメインにある
- 委譲は実装の丸投げであって設計判断の丸投げではない。判断が必要な分岐は委譲前にメインが決める
- メインが直接実装した部分は、なぜ委譲しなかったかを一言添えて報告する
